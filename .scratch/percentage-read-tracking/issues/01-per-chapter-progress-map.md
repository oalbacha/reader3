# 01: Track reading progress per chapter, not as a single contiguous position

**What to build:** `state.json` stores how far the reader has actually scrolled into *each* chapter (a map from chapter index to that chapter's own max fraction reached, monotonic per chapter), instead of one global "current chapter + scroll fraction" pointer. The overall "percent read" shown on the library card and in the reader is the length-weighted sum of each chapter's own fraction. Briefly opening a later chapter to preview it no longer implicitly credits the unread chapters in between as fully read — only that chapter's own (partial) contribution changes. Existing `state.json` files are migrated once on first load so already-tracked percentages don't regress: chapters before the old `last_chapter` are seeded as fully read, and the old `last_chapter` is seeded with the old `last_scroll` fraction.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [x] Scrolling in chapter N updates only chapter N's stored fraction (monotonic — never decreases for that chapter); it does not mark other, unvisited chapters as read.
- [x] Overall percentage = `sum(chapter_length[i] * chapter_fraction[i] for i in all chapters) / total_length`.
- [x] Reproduce the reported bug and confirm it's fixed: read through chapter 3, then open chapter 9 once via the TOC (without reading chapters 4–8) — the overall percentage increases only by chapter 9's own partial weight, not as if chapters 4–8 were also read.
- [x] Old `state.json` files without a per-chapter map are migrated once on load, preserving the previously displayed percentage (per the seeding rule above) rather than resetting to whatever the new map alone would compute.
- [x] The `/api/progress/{book_id}` response shape and the library/reader percentage fields are unchanged from the caller's perspective — this is a storage/computation change, not an API contract change.

## Comments

Implemented in `server.py`: `state.json` now has a `chapter_progress` dict (`{str(chapter_index): max_fraction}`). `default_state()` includes it; `load_state()` migrates old-format files once (`_migrate_chapter_progress`: chapters before the old `last_chapter` seeded to `1.0`, the old `last_chapter` seeded to the old `last_scroll`) and persists the migration immediately via `save_state()` so it only happens once. `compute_overall_progress()` computes the length-weighted sum from `chapter_lengths()` + the map. `update_progress()` (`/api/progress/{book_id}`) now updates only the posted chapter's own fraction (`max(prev, frac)`) and recomputes overall progress from the full map; it still returns `{"progress", "status"}` as before. `set_status()` also clears `chapter_progress` when marking a book unread, so a fresh restart doesn't leave stale per-chapter fractions behind.

Verified by running the real server (`python3 server.py`, temporarily on a scratch port, reverted afterward) against a copy of a real book's data folder: (1) a synthetic clean migration exactly reproduced the previously-shown percentage when chapter lengths hadn't drifted; (2) posting chapter 3 to 60% then chapter 9 to 10% via `/api/progress` left chapters 4–8 at 0 in the map and only added chapter 9's own weighted contribution to the overall percentage (confirmed against what the old buggy formula would have shown, which was much higher); (3) `/api/progress` response shape unchanged (`{"progress": ..., "status": ...}`). One caveat: the specific real book file used for manual testing had independent historical drift in `chapter_lengths` (from an unrelated earlier commit fixing dropped epub chapters), so migrating *that* file's stale `progress` value did not reproduce the old number — this is pre-existing data drift orthogonal to this ticket, not a flaw in the migration logic (confirmed by an isolated synthetic test using fabricated old-format state.json against the same book's current, non-drifted lengths, which reproduced the prior percentage exactly).

# 02: Format highlighted code as backticks/fenced code blocks in the Obsidian export

**What to build:** Highlighted text is stored as fully flattened plain text with no formatting, so a code snippet a reader highlights currently renders as a plain unformatted bullet, indistinguishable from prose. At export time, re-derive whether a highlight was code by reparsing the book's original chapter HTML and checking where the highlight's stored position offset falls: if the full highlighted span sits inside a `<pre>` element, render it as a fenced code block; if it sits fully inside an inline `<code>` element that isn't part of a `<pre>`, render it with inline backticks. A fenced code block uses the source's code-language hint when the original HTML provides one, defaulting to `ts` when it doesn't. Anything that only partially overlaps a code region, or has no usable position offset at all (older highlights, or standalone notes), renders as a plain bullet, unchanged from today — no guessing.

**Blocked by:** None (can start immediately, independent of ticket 01)

**Status:** ready-for-agent

- [x] A highlight whose full text span is contained within a `<pre>` in the source chapter HTML renders as a fenced code block in the export.
- [x] The fenced block's language tag comes from the source HTML's code-language hint when present, and defaults to `ts` when absent.
- [x] A highlight whose full text span is contained within an inline `<code>` (not inside a `<pre>`) renders with inline backticks around the text.
- [x] A highlight that only partially overlaps a `<pre>`/`<code>` region (starts in prose and continues into code, or vice versa) renders as a plain bullet — no partial or best-guess formatting.
- [x] A highlight or note with no position offset (including all standalone notes) always renders as a plain bullet, never attempts code detection.
- [x] Verify against at least one real book in the library that contains highlighted code (e.g. a technical book with `<pre>`/`<code>` in its chapter HTML) and confirm the exported Markdown renders as a proper fenced block or inline code, matching the source.
- [x] A highlight of ordinary prose (no code involved) renders exactly as it does today — plain bullet, no regression.

## Comments

Implemented in `obsidian_sync.py`, sharing the same `_build_position_index()` helper added for ticket 01: while walking each chapter's reparsed HTML it also records, per whitespace-delimited word, whether it sits under a `<pre>` ancestor (and that `<pre>`'s `data-code-language`, defaulting to `ts`) or under a stray `<code>` outside any `<pre>`. `_classify_code()` takes a highlight's `[offset, offset+len(text))` range, finds every word span overlapping it, and returns a fenced block only if *all* overlapping words are inside the same kind of `<pre>`, inline backticks only if *all* are inside a stray `<code>`, and `None` (plain bullet, unchanged) for any partial mix or a missing offset.

Verified with throwaway scripts (not committed): a real `<pre data-code-language="ts">` block and a real inline `<code>boolean</code>` span from `Programming TypeScript by Boris Cherny_data/book.pkl` (chapter `ch03.html`) rendered as an expected fenced `ts` block and inline backticks respectively; a highlight whose offset was deliberately shifted 10 characters into that same `<pre>` block (spilling into the following prose) correctly fell back to a plain bullet; a highlight with no offset rendered as a plain bullet unconditionally; a fabricated chapter with an explicit `data-code-language="python"` `<pre>`, a `<pre>` with no language attribute, and a stray inline `<code>` confirmed the explicit language is honored, the default `ts` applies when absent, and inline detection works independent of block detection. Also ran the real render against every book in the library that already has captured highlights: `Programming TypeScript` (293 real highlights, many with real offsets) produced 24 real fenced code blocks and 2 real inline-code bullets that visually match the source chapter's code, while plain prose highlights throughout stayed unchanged plain bullets; the two other books with real highlight data (`Automate the Boring Stuff with Python`, `Customer Success`) have zero highlights with a stored offset (all pre-date the offset feature), so they correctly produced zero fenced/inline blocks -- exercising the "no offset" fallback at scale with real data.

One pre-existing data-quality caveat noted but out of scope for this ticket: a few real highlights' stored `offset` no longer points at the exact substring in the current chapter text (e.g. one "can do" highlight's offset now lands mid a different, code-containing sentence), presumably from the book being reprocessed after the highlight was captured. Per the ticket's own design (offset is a "position hint," trusted as given, with no requirement to cross-check it against the highlight's stored text), this can occasionally cause a stale highlight to be classified based on whatever HTML now sits at that offset rather than the text it originally captured. This is a pre-existing offset-staleness risk in the app, not introduced by this change, and both tickets explicitly scope classification to "check where the offset falls," not to revalidate the offset itself.
